# Gameplay Fixes From Classic

This document tracks parity issues where the comparison against the
`e761b745d91983f4ba9803b670bae5208dbb8717` classic baseline exposed either
gameplay bugs or parity scaffolding problems. The `Classification` column
distinguishes visible gameplay changes from recorder, harness, golden, and
safety-only fixes.

`wip/parity-with-classic` means the modern gameplay branch was changed to match
classic behavior. `parity-companion` means the classic companion recorder was
changed because the e761 behavior was judged to be a bug that should not be
preserved.

| Issue | Classification | Side fixed | Effect | Why that side was fixed |
|---|---|---|---|---|
| Recorder baseline included post-e761 OpenGlad history | Scaffolding | `parity-companion` | The companion branch was rebuilt from raw `e761b745d91983f4ba9803b670bae5208dbb8717` and reimplemented only the parity recorder/dumper support on top of it. | Golden recordings must represent the chosen classic baseline plus instrumentation. Keeping normal OpenGlad development after e761 in the companion branch made the baseline inauthentic. |
| Golden recordings from the wrong baseline | Scaffolding | Golden recordings on `wip/parity-with-classic` | Golden JSON recordings were regenerated from the rebuilt e761 companion recorder. | The branch should compare against authentic e761 behavior, not recordings produced from a later post-e761 companion history. |
| Parity runner event/RNG drift | Scaffolding | `wip/parity-with-classic` | The runner was aligned to classic RNG observation, event capture, metadata normalization, score event handling, positional-sound visibility, and screen-completion behavior. | These were harness differences, not gameplay differences. The modern parity runner needed to replay and compare the same observable stream that the e761 recorder emits. |
| Empty scenario completion stream | Scaffolding | `wip/parity-with-classic` | Empty scenarios now keep classic completion events such as `set_end` and `end_game` instead of filtering them out. | The harness was dropping real classic events. The e761 recorder was correct to include the completion stream. |
| Small slime no-ranged flag | Visible gameplay | `parity-companion` | Small slimes could incorrectly fire free blob projectiles at range. They should still be able to melee, but should not launch ranged blobs. | e761 had a loader typo: it compared `order` to `FAMILY_SMALL_SLIME` instead of comparing `family`. The surrounding setup and modern descriptor both clearly intended `BIT_NO_RANGED` for small slimes. |
| Giant skeleton bloodspot | Visible gameplay | `parity-companion` | Giant skeletons left a bloodspot/death stain when dying. They should behave like the other undead/no-bloodspot enemies. | e761 omitted `FAMILY_GIANT_SKELETON` from the same no-stain death class as skeleton/ghost/tower. The modern descriptor already had `leaves_bloodspot = false`, which matches the intended undead behavior. |
| Expired poison cloud still acting | Visible gameplay | `parity-companion` | A cloud whose lifetime had expired could still attack and schedule movement during the same tick it died. | Dead effects continuing to act is a classic bug. The correct behavior is to return immediately after marking the cloud dead and running `death()`. |
| Poison cloud random-walk underflow | Visible gameplay | `parity-companion` | Poison cloud drift was biased because `random(3) - 1` underflowed when `random(3)` returned zero. Negative directions collapsed or became implementation-dependent before the walk command was queued. | The intended random walk is `-1`, `0`, or `1` per axis, excluding `0,0`. Casting to signed before subtracting restores the obvious intended behavior. |
| Generator spawn direction underflow | Visible gameplay | `parity-companion` | Generator firing/spawn direction could corrupt the intended `-1`, `0`, or `1` random direction when unsigned subtraction underflowed. | The generator path intended signed direction choices. Casting to signed before subtracting avoids implementation-dependent large values. |
| Slime/weapon auto-attack false positive | Visible gameplay | `parity-companion` | Ordinary projectiles could trigger `living::collide()` as if they were attackable targets. In the slime case, a soldier's thrown knife (`ORDER_WEAPON`, `FAMILY_KNIFE == 0`) falsely matched generator `FAMILY_TENT == 0`, causing the slime to start an attack response to the projectile itself. | e761 compared raw family IDs without considering object order. Family IDs are reused across orders, so the predicate must be order-aware: living and generators are attackable, while only explicitly attackable weapon objects such as glow, tree, and door should be auto-attackable. |
| Ghost animation sentinel/OOB access | Safety/scaffolding | `parity-companion` | Ghost animation could read the `-1` sentinel or adjacent memory after the animation cycle moved past the valid sequence. | This was unsafe memory/sentinel behavior, not intended gameplay. The companion was changed to complete the animation when `cycle >= sequence_length`. |
| Fire elemental animation sentinel/OOB access | Safety/scaffolding | `parity-companion` | Fire elemental animation had the same stale-cycle sentinel/OOB behavior as ghost animation. | Same root cause as the ghost case: classic was reading beyond the valid animation sequence, so the companion was bounded instead of preserving undefined behavior. |
| Druid faerie summon level | Visible gameplay | `wip/parity-with-classic` | Druid-summoned faeries inherited the druid's level in the modern branch, changing their stats and combat strength. | e761 did not copy the summoner's level for this summon path. The modern helper introduced extra state, so the branch was changed to create the faerie and set only the classic fields. |
| AI `direct_walk()` fire check | Visible gameplay | `wip/parity-with-classic` | Ranged AI could walk instead of shooting, or shoot only after different turning, because the branch normalized the target vector before checking whether it could fire. | e761 passes the raw target vector into `fire_check()`, preserving slope information for facing/aiming. Normalized deltas are appropriate for movement steps, not for the fire-vs-walk decision. |
| Facing/turn parity | Visible gameplay | `wip/parity-with-classic` | Actors could rotate along a different path, affecting facing frames, `lastx`/`lasty`, attack direction, and firing timing. | The branch defensively clamped invalid/transient directions to `FACE_UP`. Classic uses the raw direction value in its modulo turn arithmetic, so the clamp changed behavior. |
| Positional death sounds | Visible gameplay | `wip/parity-with-classic` | Death sounds could play when classic would consider the death off-screen or otherwise not audible through positional sound visibility. | e761 gates positional death sounds by visibility. The branch emitted too broadly, so the branch sound path was restricted to classic visibility rules. |
| Combat score/XP timing | Visible gameplay | `wip/parity-with-classic` | Score and XP changes could occur at different ticks or be attributed differently from classic combat. | Modern combat refactoring moved reward sequencing away from classic behavior. The branch was changed so hit rewards, owner/weapon attribution, and melee/ranged scoring occur in the classic locations. |
